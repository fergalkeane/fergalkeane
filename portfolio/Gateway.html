01 — Overview

One workspace for a workflow that was scattered across a dozen systems.

Gateway is an operations console that consolidates the fragmented toolchain ESA mission-support teams use to run a maintenance cycle into a single, state-aware workspace — orchestrating existing systems rather than replacing them.

What it is

A web console that sits above ESA's existing operational tools and presents one continuous workspace for running a maintenance cycle end to end.

Who it's for

Primary: mission-support operators and maintenance engineers working live cycles. Secondary: shift leads who audit work and run handovers between shifts.

Core problem

A single maintenance cycle spanned 12+ disconnected tools. The constant context-switching — not any one tool — was driving errors and cognitive fatigue in an environment with no tolerance for either.

Why it matters

Business: errors and lost time on mission-critical tasks carry safety, compliance and cost exposure. User: sustained high cognitive load and risky handoffs are unsafe and unsustainable on a 24/7 console.

02 — Problem Definition

The real problem was the seams, not the tools

Each tool did its job well in isolation. The failure was in the connective tissue: operators were the integration layer, manually carrying state, data and context across twelve systems while staying accountable for every transition.

Constraints that shaped the brief

Technical

Orchestrate, don't replace

Source tools were certified and load-bearing. Gateway had to coordinate them through existing data feeds — replacing them was off the table.

Operational

Live 24/7 console

Control rooms never stop. Nothing could disrupt an active cycle, and any new surface had to be learnable without pulling operators off shift.

Compliance

Full traceability

Every value and action had to be auditable back to its source system. Aggregation could never obscure provenance.

Environment

Glance-critical

Low-light rooms, large shared displays, and operators under pressure — status had to read correctly in a glance from across the room.

Success criteria

  • Cut the number of tool switches required to complete one cycle.
  • Reduce task errors, especially at state transitions and handovers.
  • Preserve end-to-end auditability with no loss of provenance.
  • Be learnable by an experienced operator within a single shift.

End-to-end design ownership, in close loop with mission ops.

I led the work from discovery through delivery: framing the problem with mission-support SMEs, mapping the maintenance lifecycle, designing the interaction model and UI, building the component system, and prototyping for validation and engineering handoff.

I partnered daily with a product manager, operations subject-matter experts, and the front-end team. To be precise about scope: I did not own the backend data contracts or the certification of the underlying source tools — my mandate was the orchestration layer and everything the operator touches.

04 — Discovery & Insights

Watching one full cycle changed the brief

Inputs included SME interviews, a tool-and-task audit of a complete maintenance cycle, and contextual observation of operators on console. The goal was to find where the work broke down, not just that it did.

Some research detail is reconstructed for this portfolio and labelled where inferred.

01

The handoffs between tools were the problem — not the tools.

Operators rated individual tools as fine. Failure clustered in the gaps: re-keying values, reconciling state, and confirming that what one system showed matched what the next expected.

02

Operators didn't want all the data — they wanted the right data for the current step.

A maintenance cycle is sequential. At any moment only a slice of the twelve tools was relevant, yet everything competed for attention at once.

03

Errors concentrated at state transitions and shift handovers.

The most dangerous moments were when a cycle moved between stages or between people — exactly where context was most likely to be dropped. Inferred from task analysis

04

Trust required provenance.

Operators would not act on an aggregated number they couldn't trace to its source system. Any summary view had to make “where did this come from?” a one-click answer.

05 — Design Strategy

Follow the lifecycle, surface only what the step needs

Before any UI, I committed to a principle: Gateway should model the maintenance lifecycle itself, presenting only the data and actions relevant to the operator's current stage — and always keeping a path back to the source system for trust.

Directions considered & why I rejected them

Rejected

One mega-dashboard showing everything

Putting all twelve tools on one screen just relocates the overload. It optimises for the demo, not the shift — and it directly violates insight 02.

Rejected

Rip-and-replace the twelve tools

Infeasible on cost, risk and certification, and explicitly out of scope. The source systems are load-bearing; the seams between them were the brief.

Rejected

A launcher / portal of links

A tidy menu of shortcuts doesn't reduce switching — it just renames it. The operator is still the integration layer, carrying state by hand.

Chosen

A state-aware lifecycle workspace

Gateway tracks where the cycle is and surfaces only the relevant datasets and actions for that stage, with every value deep-linked back to its source. It reduces switching without hiding provenance.

06 — Execution · Key Decisions

Four decisions that carried the design

Each screen exists to serve a specific operational behaviour. The decisions below are organised by the problem they solve, not by the order they were drawn.

Decision 01

A lifecycle spine, not a navigation menu

Navigation models the maintenance cycle's stages directly, so the interface always answers “where am I and what's next?”. Why: orientation cost was a hidden tax on every switch — encoding the workflow into the structure removes it.

Information ArchitectureWayfinding

Stage stepper anchoring the workspace

Decision 02

A state-aware workspace that shows only the current step

The workspace serves only the datasets and actions relevant to the active stage, with the rest one deliberate step away. Why: directly attacks the cognitive-load insight — relevance over completeness.

Decision 03

Provenance on every aggregated value

Each consolidated figure carries a source affordance that links straight back to the system of record. Why: operators won't act on numbers they can't trace — and compliance demanded full auditability.

Decision 04

Safe-by-default actions at the riskiest moments

State transitions and handovers use confirmation and reversible patterns, with status that reads from across a low-lit room. Why: errors clustered exactly here — so the friction is intentional and placed precisely.

09 — Reflection

What I'd carry forward

What worked

The lifecycle spine earned trust early

  • Modelling the workflow in the structure made the concept legible to SMEs in the first review.
  • Treating provenance as a first-class affordance turned aggregation from a risk into a feature.
What I'd improve

Measure earlier, test on console

  • Capture a quantitative baseline before design, so impact is attributable rather than reconstructed.
  • More usability testing in the real low-light room, and explicit design for degraded / offline states.
What I learned

Orchestration beats replacement

  • In legacy-heavy enterprise, the highest-leverage design often lives in the seams, not the tools.
  • Trust is a design material — and tight constraints, read correctly, are the clearest brief you'll get.
